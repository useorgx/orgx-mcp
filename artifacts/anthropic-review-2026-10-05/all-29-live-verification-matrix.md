## Cost and authorization limitations

A **zero dollar cap does not guarantee zero execution**. At this exact source head, `evaluateSpawnBudgetPreflightResult` blocks only when `budget_check.within_cap === false`. `buildRouteTaskEstimateSummary` sets that to true for a zero-cost route and null if estimated cost is absent; both can proceed to later gates. Therefore, do not issue a real valid dispatch solely because `max_cost_usd:0` is supplied. First obtain explicit canary authorization or use a guaranteed pre-execution schema/auth rejection. If testing a positive estimate above cap is approved, retain the actual estimate and returned budget rejection plus before/after run counts; never infer this rejection from the supplied cap alone.

`manage_lifecycle` resume/retry and app-only `resume_agent_run` do not expose the same caller budget contract as delegation. Initiative launch likewise is a separate action path. Test each execution path under its actual workspace/provider controls and consent; a delegation estimate or budget refusal does not prove these paths safe or functional.

The directory's four metered information tools legitimately use `readOnlyHint:false` for allowance accounting. That accounting does not imply permission to mutate business records. `orgx_open_decision_review` is read behavior with a retained write grant; it opens a human gate and must never be described as approval.

Full happy-path verification remains incomplete until the real valid tool cases and widgets have receipts. A planned matrix, SDK fakes, rejection-only tests, CI, merge, deployment, successful refresh, form save, actual submission, and provider acceptance are separate states. Keep the submission's self-tested claim aligned with the actual completed Inspector and Claude evidence, including any clearly declared execution limitations.
